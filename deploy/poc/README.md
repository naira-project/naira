# RFC-009 proof of concept

Everything RFC-009 proposes, running on one kind cluster. Throwaway: the
cluster, the registries and the certificates here are demo scaffolding, not a
proposal for how any of this should look in CI.

## Run it

```bash
deploy/poc/up.sh                      # kind cluster + HTTP registry (images)
deploy/poc/build-images.sh            # 11 images -> localhost:5001
deploy/poc/publish.sh                 # OCI chart + OCM component version
kubectl apply -n argocd -k ../../../component-testbed/argocd/environments/poc
tilt up                               # inner loop, same charts
```

## What it proves

| RFC-009 | Evidence |
|---|---|
| §1 two charts, split on lifecycle | `deploy/charts/naira` (first-party) and `component-testbed/charts/naira-dependencies` (tier) install independently |
| §2 values-driven plugin sidecars | `helm template` renders the catalog pod's 8 containers identically to `deploy/dev/.../catalog.yaml`; the generated `plugin-config` ConfigMap is byte-identical to the hand-written one; RBAC rules match |
| §2 `enabled: false` drops a plugin | `values-poc.yaml` disables `openmetadata`; the pod renders 7 containers instead of 8 |
| §3 dual publish | `publish.sh` pushes the OCI chart and builds an OCM component version carrying 11 digest-pinned resources, transfers it to a registry, and reads it back |
| §3 no hand-written tags | every image tag falls back to `.Chart.AppVersion`; `deploy/charts/catalog`'s `sha-9f5ef2b` is gone |
| §4 thin derived Tiltfile | `tilt ci` exits 0 with "All workloads are healthy" from an empty cluster: it derives the build set from `catalog.plugins`, builds 9 images, and brings the catalog up 7/7 (six plugins — `openmetadata` is disabled in `values-dev.yaml` and Tilt correctly skips it). Adding a plugin touches no Tilt code |
| §6 ArgoCD from a released artifact | both Applications sync from `oci://…/charts/<name>:0.1.0-poc`; the catalog pod runs 8/8 from registry images, never side-loaded |
| §7 one-shot Jobs fight auto-sync | partially — a running Job held the Application out of sync, but the OpenBao/selfHeal hazard itself is untested. See findings 4 |

## Findings

Things that cost time and belong in the RFC.

### 1. `condition:` breaks on subcharts with a strict schema

`condition: mlflow.enabled` injects an `enabled` key into the subchart's own
values. mlflow 1.11.7 ships a `values.schema.json` with `additionalProperties:
false` and rejects it. Helm **tags** live in the parent and are never passed
down.

Tags buy something else: one `monitoring` tag gates both kube-prometheus-stack
and the ServiceMonitors in `templates/`, so the CRs cannot be applied without
the operator that defines them. That constraint is structural rather than a
validation rule.

### 2. `global.imageRegistry` leaks into every subchart

Setting it for first-party images rewrote the images of litellm's bundled
bitnami PostgreSQL and tripped bitnami's image-verification guard. First-party
registries must be chart-local values, never Helm globals.

### 3. `fail` in a `_`-prefixed template never runs

Helm treats `templates/_*.tpl` as partials: it parses them but never executes
their top-level content. A validation guard in `_validate.tpl` silently does
nothing. Renamed to `templates/validate.yaml`, which renders no objects and
does fail.

### 4. Auto-sync vs. one-shot Jobs — seen, but transient

While `naira-dependencies` was converging, the Application sat `OutOfSync` for
several minutes on `Job/litellm-migrations` and three generated Secrets. It
reached `Synced` once the migration Job completed and has stayed there across a
hard refresh.

So this is **not** a reproduction of RFC-009 §7's hazard. That hazard is
`selfHeal` contending with an init flow that deletes `openbao-0` by hand, and
nothing here exercises it. What this does show is that a one-shot Job is enough
to hold an Application out of sync while it runs — worth knowing before the
OpenBao migration, but it is not evidence that the §7 risk is real.

The §7 risk stays untested. It needs the testbed cluster.

### 5. Charts that generate random secrets — open question

`Secret/litellm-masterkey`, `Secret/naira-dependencies-postgresql` and
`mlflow-flask-server-secret-key` are generated by their upstream charts. If
those values are re-randomised on every `helm template`, an auto-synced
Application can never converge.

Observed here: they were `OutOfSync` during the initial sync and are not now.
`mlflow-flask-server-secret-key` currently reports no sync status at all. That
is consistent either with the charts using `lookup` to keep existing values, or
with ArgoCD suppressing the diff — this PoC did not establish which.

Worth settling before any environment runs auto-sync over these charts, because
if it is the former the ExternalSecret shape in P4 is not only safer but the
only thing GitOps converges on. Currently an open question, not a finding.

### 6. ArgoCD's OCI Application shape is not the one in RFC-009 §6

Four things all had to be right at once on ArgoCD 3.5.2, and each wrong one
produced a different misleading error:

| | |
|---|---|
| `repoURL` | must carry the `oci://` scheme **and** the chart path; `chart:` is still required by validation but the resolver uses the URL |
| `AppProject.sourceRepos` | matches the scheme too — a bare host entry rejects an `oci://` Application |
| repository secret | must match the Application's `repoURL` **exactly**; `repo-creds` prefix matching did not apply `insecure` |
| TLS | `insecureOCIForceHttp` did not work against a plain-HTTP registry in any combination tried. The charts are served from a second, TLS registry with its CA in `argocd-tls-certs-cm` |

RFC-009 §6's example (`repoURL: ghcr.io/naira-project/charts` + `chart: naira`)
is the `type: helm` + `enableOCI` form. Against ghcr, with TLS and credentials,
it is the right one — but the RFC should say which form it means.

### 7. Two registry host entries, not one

`localhost:5001` is how a laptop pushes; `naira-poc-registry:5000` is how the
kubelet pulls. Both need a containerd `certs.d` entry or images fail with
`ErrImagePull` **only on the GitOps path**, while Tilt keeps working.

### 8. Resource limits the RFC never mentions

LiteLLM OOMKills at 1Gi (component-testbed's HelmRelease already uses 2Gi).
MLflow 3.x OOMKills at 1Gi with the chart's default 4 workers, and its new
security middleware rejects the kubelet's probes unless `--allowed-hosts` is
set — the container restarts forever with a healthy-looking log.

## Running both

Tilt and ArgoCD cannot own the same namespaces at once. Running `tilt ci` while
the Applications were auto-syncing restarted the PostgreSQL StatefulSet and
`tilt ci` gave up on it. From an empty cluster — Applications deleted,
namespaces gone — the same run succeeds.

For the demo, pick one: either the Applications are synced, or Tilt is up.
Switching means `tilt down --delete-namespaces` then re-applying
`argocd/environments/poc/`, or the reverse.

## Not proven here

- OpenBao and ESO. They live in the testbed cluster; the migration hazard in
  §7 stays untested.
- OpenMetadata. It pulls MySQL, Elasticsearch and Airflow and does not fit on
  one kind node. Declared in the chart, off by default.
- Signing. The OCM component version is signable; no key exists yet
  (open question 6).
- Publishing to ghcr. Everything here targets local registries.
- Tilt's `live_update`. `tilt ci` proves the Tiltfile builds and deploys; it
  does not exercise the fast edit-reload path, which is the reason to use Tilt
  at all.
