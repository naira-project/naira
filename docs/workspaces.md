# Test workspace and cluster registrations

Naira currently provides exactly one hardcoded workspace: `test-workspace`.
It is shared by all authenticated users, who can add, view and edit its cluster
registrations. There is no per-user ownership or workspace management: workspaces
cannot be created, renamed, edited or deleted. Cluster names are case-sensitive
and unique within the workspace.

## API

All routes require a Bearer token:

| Method | Route | Input |
| --- | --- | --- |
| GET | `/v1/workspaces` | Returns only `test-workspace`. |
| GET | `/v1/workspaces/test-workspace` | Returns the fixed workspace ID and name. |
| POST | `/v1/workspaces/{workspaceID}/registrations` | Registration configuration below. |
| GET | `/v1/workspaces/{workspaceID}/registrations` | Lists registrations in the test workspace. |
| GET | `/v1/workspaces/{workspaceID}/registrations/{id}` | Returns one registration. |
| PUT | `/v1/workspaces/{workspaceID}/registrations/{id}` | Full replacement of editable fields. |
| POST | `/v1/workspaces/{workspaceID}/registrations/{id}:test` | Test the saved connection, without a request body. |

`{workspaceID}` must be `test-workspace`; any other ID returns 404. Workspace
creation, update and deletion methods are not supported (405).

Example registration input:

```json
{
  "name": "production-cluster",
  "credentialRef": "operator-managed-reference",
  "kubernetes": {
    "apiEndpoint": "https://kubernetes.example.com:6443",
    "context": "production"
  }
}
```

Registrations describe Kubernetes clusters only; there is no `kind` discriminator.
The `kubernetes` connection object is required for creation and updates.

Cluster IDs and timestamps are generated by the backend. Unknown fields,
including supplied ownership, IDs, fingerprints and validation results, are
rejected. Registration updates cannot change identity or workspace. Changing
connection configuration invalidates the previous validation result. PUT returns
204; GET retrieves the updated record.

Authentication and the fixed workspace scope are checked before accessing
registrations, including direct application-service calls. All valid signed-in
users have the same access; there are no workspace-specific permissions yet.
An unknown workspace or registration returns 404.
Conflicts return 409; invalid input returns 400. API responses omit credential
references and values, and errors do not echo request data. A reference must be
provided again when updating a registration.

## Manual connection tests

The `:test` suffix is a custom action on a registration, following the same
convention as `:run` on plugins. It is not a child resource; the old `/test`
route is not supported.

The [function call diagram](diagrams/cluster-connection-test.excalidraw) can be
opened in Excalidraw or a compatible VS Code extension.
For a beginner-friendly explanation of the two clusters, Secrets and access
checks, see the [credential access diagram](diagrams/cluster-access-explained.excalidraw).

Save the registration through the API, then call its `:test` action. This is a
synchronous, read-only check, not discovery. The API returns HTTP 200 for both a
completed READY result and a completed FAILED result. Results include a check
name, PASS/FAIL, a safe error code and message, and a timestamp. The last result
is saved in memory and returned with the registration. Runnable API scenarios are
in [local-e2e](../local-e2e/README.md).

The test checks the approved credential, selected kubeconfig context and matching
HTTPS endpoint, TLS connectivity, `kube-system` UID, and cluster-wide list access
to namespaces, Deployments and Services. This initial scope is not namespace
filtered. API reads use a limit of one item; responses are not imported into the
Catalog. The overall timeout is 30 seconds and each request is bounded to 8 seconds.

The cluster becomes READY only when all checks succeed. An existing installation
UID is never replaced by a different observed UID. Configuration changes during
a test produce HTTP 409 instead of applying a stale result. Editing a connection
or credential reference resets its status to PENDING and clears the old report.
Changing a credential's value at the same reference requires another manual test;
there is no automatic invalidation or freshness policy yet.

### Operator-approved credentials

The only supported credential source is a Kubernetes Secret containing a
self-contained kubeconfig for the external cluster. Authentication requires
exactly one method: an embedded ServiceAccount token, or an embedded client
certificate and private key (`client-certificate-data` and `client-key-data`).
Incomplete pairs, mixed methods and basic authentication are rejected. The target
API verifies the client certificate and applies RBAC to its identity; it need not
be a ServiceAccount. Server CA data verifies the API server, not the client.
Use `kubernetes-secret:namespace/name#key` and set
`CLUSTER_CREDENTIAL_SECRETS` to a JSON object mapping workspace IDs to lists of
exact `namespace/name#key` entries, for example:

```json
{"test-workspace":["idp-system/naira-registry-test-reader-access#kubeconfig"]}
```

No credentials are approved by default. Missing or empty workspace entries deny
access. The workspace comes from the authorized, stored cluster registration;
the store checks the workspace/reference pair before calling the Kubernetes API.
There is no global fallback. Sharing a credential requires explicitly listing it
under each workspace. The former comma-separated configuration is rejected.

The backend runs in Kubernetes. Its own ServiceAccount needs `get` access to the
named Secrets. At application startup, `rest.InClusterConfig()` configures this
Secret client; it is never used to authenticate to the target cluster.

Kubeconfigs are limited to 1 MiB. Local file references,
external credential/CA files, `exec` commands,
auth providers, impersonation, proxy URLs and disabled TLS verification are
rejected. The endpoint must match the selected server; no local or in-cluster
credential fallback is used for the target connection. Environment proxies are
not used for these direct-access tests.

Certificate/key parsing and matching are checked before network requests. The
target API must trust the client certificate's issuer and accept its validity and
usage. Authentication alone grants no resource permissions. Tests neither issue
nor renew certificates; rotating the Secret requires another manual test.

Every signed-in user in the temporary shared workspace can use every reference
approved for that workspace. The allowlist is an operator trust boundary, not per-user Secret
authorization. Treat approved kubeconfigs as trusted configuration: their targets
must be appropriate for backend network access. Responses never include credentials,
credential references or raw upstream error messages.

For the Helm deployment, configure named Secrets in the release namespace:

```yaml
catalog:
  clusterValidation:
    credentialSecrets:
      test-workspace:
        - name: naira-registry-test-reader-access
          key: kubeconfig
```

The chart sets the allowlist and creates a namespaced Role with only `get` on
those resource names. It neither creates the credential Secrets nor changes their
values. Existing plugin RBAC can already grant wider permissions to the shared
ServiceAccount; the Secret store still enforces its exact workspace-scoped allowlist.
See [live lab](../k8s-real-test/README.md) for examples.

Kubernetes-specific checks are in `plugins/pkg/kubeaccess`. For this first version
they run in-process through an injected adapter, not a new plugin gRPC method.
`catalog/internal/clusterregistry` owns registrations and atomic result persistence.
Its `connectiontest` subpackage separates three responsibilities:

- `Service` authorizes the operation, runs the test and saves the final result.
- `SecretStore` loads kubeconfigs only from Secret keys approved for the workspace.
- `KubernetesTester` loads a credential and delegates API checks to `kubeaccess.CheckAccess`.

The application wires them explicitly as `SecretStore → KubernetesTester → Service`.
The subpackage depends on the registry, not the other way around. Stored result
types stay in the registry as part of cluster state. This operation does not invoke `Collect`.

## Current limitations

- Cluster registrations and edits are in-memory and process-local. They are lost
  on restart and not shared between backend replicas. The fixed workspace is
  always present, even when there are no clusters. This does not satisfy the
  persistence requirement of issue #291.
- Saving performs structural validation only; new registrations remain PENDING
  until a manual test passes. Tests do not schedule discovery or import resources.
- Existing catalog graph, plugin operations and schedules are **not workspace
  scoped** and do not consume these registrations. This feature is not yet
  end-to-end tenant isolation for discovered data.
- This temporary shared workspace is not a tenant isolation or workspace
  authorization implementation. There is no credential rotation/revocation workflow or
  membership management.
