# Workspaces and source registrations

Naira workspaces are flat and have one immutable owner, identified by the issuer
and subject of a verified OIDC token. Every authenticated user may create their
own workspaces. Names are case-sensitive and unique per owner. A user may own
multiple workspaces; each workspace may contain multiple source registrations.
There are no groups, parent workspaces, ownership transfers or delete operations.

## API

All routes require a Bearer token:

| Method | Route | Input |
| --- | --- | --- |
| POST | `/v1/workspaces` | `{"name":"production"}` |
| GET | `/v1/workspaces` | Lists only the caller's workspaces. |
| GET | `/v1/workspaces/{workspaceID}` | Returns an owned workspace. |
| POST | `/v1/workspaces/{workspaceID}/registrations` | Registration configuration below. |
| GET | `/v1/workspaces/{workspaceID}/registrations` | Lists registrations in an owned workspace. |
| GET | `/v1/workspaces/{workspaceID}/registrations/{id}` | Returns one registration. |
| PUT | `/v1/workspaces/{workspaceID}/registrations/{id}` | Full replacement of editable fields; omit `kind`. |

Example registration input:

```json
{
  "name": "production-cluster",
  "kind": "kubernetes",
  "credentialRef": "operator-managed-reference",
  "kubernetes": {
    "apiEndpoint": "https://kubernetes.example.com:6443",
    "context": "production"
  }
}
```

Ownership comes from the token, not request fields. IDs and timestamps are
generated by the backend. Unknown fields, including supplied ownership, IDs,
fingerprints and validation results, are rejected. Registration updates cannot
change identity, workspace or kind. Changing connection configuration invalidates
the previous validation result. PUT returns 204; GET retrieves the updated record.

Authorization is enforced in the application services as well as before parsing
workspace-scoped HTTP requests. Foreign and missing workspaces both return a
generic 403. A registration not found within an owned workspace returns 404.
Conflicts return 409; invalid input returns 400. API responses omit credential
references and values, and errors do not echo request data. A reference must be
provided again when updating a registration.

## UI

Open **Workspaces** from the overview. Create or select a workspace, then register
or edit its clusters. Authentication continues to use the existing login shell;
the workspace model has no dependency on an external tenancy platform.

## Current limitations

- Stores are in-memory, process-local and empty after restart. Multiple backend
  replicas do not share registrations or workspaces. This does not satisfy the
  persistence requirement of issue #291.
- Registration performs structural validation only. It does not resolve or
  authorize access to credential references, contact Kubernetes, or run discovery.
  New registrations remain PENDING. Future credential resolution must enforce
  permission to use the referenced secret, not merely permission to edit a workspace.
- Existing catalog graph, plugin operations and schedules are **not workspace
  scoped** and do not consume these registrations. This feature is not yet
  end-to-end tenant isolation for discovered data.
- There is no credential rotation workflow, sharing or membership management.
